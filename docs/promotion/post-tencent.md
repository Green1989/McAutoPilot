# WorkBuddy × 麦当劳 1024 参赛作品：McAutoPilot——基于官方 MCP 的"午饭自动驾驶"

> 摘要：一个跑在 GitHub Actions 上的 Agent，每天早上 10 点自动连上麦当劳官方 MCP，感知门店菜单/优惠券/历史订单/营养缺口，做出一笔带编号理由的午饭决策并写进公开日记。本文分享它的架构、官方 MCP 集成的四个工程坑与安全设计，附五分钟私有部署指南。

## 一个会自己写日记的仓库

我的 GitHub 仓库 `DECISIONS.md` 里有一条这样的记录（真实生成，无人工编辑）：

> **今日决策**：芝士安格斯厚牛堡 —— 实测算价 ¥31.5
> 1. 蛋白质 32g 达标（目标 ≥30g），下午写码不困
> 2. 热量 696kcal 落在 480-820 的午餐甜区
> 3. 性价比 1.02g 蛋白/元，高于 1.0 的及格线
> 数据源：广州长兴路餐厅 · 123 个在售餐品 · 2 张可用券

这是 [McAutoPilot](https://github.com/Green1989/McAutoPilot) 的 Day 1 日记。每天北京时间 10:00，一个 GitHub Actions 定时任务醒来，完成"感知 → 决策 → 算价 → 记录"的完整闭环，并把日记 commit 回仓库——commit 历史就是这本日记的连载本身。

## 为什么做这个

"中午吃什么"是打工人每天都要回答的高频决策，痛点不在"没得选"，而在信息过载：30 张优惠券不知道哪张最划算；想换口味又不知道最近吃过什么；昨天吃太咸了，今天其实该补点蔬菜——但没人记得自己的营养缺口。

所以我把这个决策外包了出去。它有记忆（点餐历史）、有约束（预算/营养上限）、有目标（划算、别重样、营养均衡），还有一本公开的决策日志——**每一次"它为什么这么选"都有据可查**。

## 系统架构

```
10:00 (cron) ──▶ 感知 ──▶ 决策 ──▶ 执行 ──▶ 记录
                 │         │        │        │
                 │         │        │        └─ DECISIONS.md + 营养台账
                 │         │        │           自动 commit（活仓库）
                 │         │        ├─ 订单草稿（默认 dry-run）
                 │         │        └─ 可选：决策卡 webhook 推送
                 │         ├─ 营养缺口 + 预算 + 券 + 换口味 + 理由
                 │         └─ 决策引擎（规则打分 v1，求解器 v2 分支验证中）
                 └─ 菜单/券/历史订单/营养/积分（麦当劳官方 MCP）
```

四层各自独立成模块（`agent/perceive.py` / `brain.py` / `executor.py` / `report.py`），单路感知失败自动降级并如实写进日记——降级本身也是决策记录的一部分。

## 官方 MCP 集成实践

接入麦当劳官方 MCP Server（`https://mcp.mcd.cn`，Streamable HTTP + Bearer Token）。实测发现 **35 个工具**，主链路用到 7 个：`query-nearby-stores`、`query-meals`、`query-store-coupons`、`order-list`、`list-nutrition-foods`、`query-my-account`、`calculate-price`。

集成过程不算平滑，四个印象最深的坑：

1. **返回是 markdown 包裹的 JSON**。多数工具返回「字段说明 + `## Original Response` + 原始 JSON」，直接 `json.loads` 必挂。适配做在统一的 `extract_json`：截取 Original Response 段再解析。
2. **营养表是 CSV 文本**。`list-nutrition-foods` 返回 `[160]{productName,...,energyKcal,...}:` 加 CSV 行——对 LLM 友好但对程序不友好，需要按表格结构解析。
3. **金额单位是分**。`calculate-price` 返回的 price/discount 均为分，渲染前要除以 100，否则日记里会出现 ¥3150 的巨堡。
4. **限流与断连**。上游限流 600 req/min，客户端做了串行调用 + 间隔控制 + 断连重建会话重试一次，公网抖动不影响主流程。

另外做了一套与真实服务**逐字段对齐**的离线 Mock：无 Token 场景自动降级，fork 后零配置即可用模拟数据走完整决策循环，CI 与本地开发都不依赖外网。

## 可解释的决策引擎

引擎不做黑盒推荐，每条决策理由都带真实数字（见开头 Day 1 引用）。规则打分引擎 v1 覆盖六条规则：营养缺口（7 天滚动均值）、单餐预算、券有效期、近期重复度惩罚、性价比、蛋白质密度。

约束求解器引擎 v2 已在开发分支完成验证：先过硬约束（预算 / 钠 ≤1500mg / 热量 ≤1200kcal），再按公开权重的归一化目标求最优，日记里会多一行「分数构成」逐项明细——比如"券价值 +1.6 · 蛋白质 +2.5 · 新鲜度 +1.5"。真实下单执行链（领券 + 创建订单）也已实现三重护栏：双开关授权、预算硬上限、订单只到"待支付"且支付永远人工完成。

## 安全与合规设计

- Token 只走 GitHub Secrets → 环境变量，代码零硬编码，仓库做过全文扫描；
- 订单等个人数据经字段白名单过滤后才落地，探针脚本输出自动脱敏；
- 默认 dry-run：执行链止步于 `calculate-price` 纯计算接口，不下单、不领券、不动账户；
- fork 后无 Token 自动进入离线 Mock 模式。

## 五分钟私有部署

1. Fork 仓库（什么都不配也能跑——无 Token 自动进 Mock 模式先看效果）；
2. 在 open.mcd.cn 申请麦当劳 MCP Token（免费，需审核，建议尽早）；
3. 你的 fork → Settings → Secrets and variables → Actions → 添加 `MCD_MCP_TOKEN`；
4. Actions 页启用 workflow（fork 默认禁用）；
5. 建议先加 Variable `MCD_PREVIEW=true` 手动跑一次，用真实数据出决策预览确认正常；
6. 删掉 `MCD_PREVIEW`，之后每天北京时间 10:00 它自动醒来写日记。

预算可通过 `MCD_BUDGET` 调整（默认 40 元）。
